# 馆藏迁库 · 宽表拆表工具

作品表分别左联接题名明细、参展明细导出的一张宽表（CSV），在网页端上传后
按作品拆回两份**带份数**的明细。SQLite 保存宽表输入与馆员登记的底账总条数；
只有全部作品都存在唯一拆分时，才允许打包下载两份明细 CSV。

在此之上提供**入库增量发布**：接收库为同一（作品号、类别、名称）下的每一份
同名明细单独建档，本工具按上次发布的份数计算增减，发放/撤销份号并打出
增量包 CSV；补传时仍在使用的份号保持不变。

## 1. 数据模型与拆分原理

设某作品有题名 T₁…Tₚ（原明细允许同名，按名称归并），各名称在题名明细中的
份数（行数）为正整数 xᵢ；参展 E₁…E_q，份数 yⱼ。

宽表是“作品表左联接题名明细、再左联接参展明细”的导出，按组合聚合后：

- 两侧都有明细：每个组合次数 `c(i,j) = xᵢ × yⱼ`，且覆盖完整笛卡尔组合；
- 只有题名明细：展名全为空，每行次数即该题名的份数 xᵢ；
- 只有参展明细：题名全为空，每行次数即该展名的份数 yⱼ；
- 两侧都无明细：题名、展名均空。

**核对时不展开重复行**：所有比较都在聚合后的 `(题名, 展名, 次数)` 行上进行，
不构造笛卡尔积；同名组合出现多行时次数自动归并求和（原明细允许同名）。

### 唯一性判定（两侧都有明细时）

1. 先做可乘性校验：`c(i,j)·c(1,1) = c(i,1)·c(1,j)`，不满足即为**冲突**；
2. 校验完整组合无缺失；
3. 以第一个题名的份数 x₁ 为自由变量，其可行取值恰为矩阵第一行各元素的
   全部公约数，枚举出全部可行拆分；
4. 用馆员登记的题名/参展**底账总条数**（各侧份数之和）过滤：
   - 无一相容 → **冲突**（页面同时列出可行的总条数候选，便于更正）；
   - 恰好一组 → **唯一可拆**；
   - 多组留存 → **待补底账**。

单侧明细、双侧均空的场景份数由组合次数直接确定，登记的底账只做一致性校验。

### 已提交状态与快照

- 每次上传或底账登记/更正都在一个 SQLite 事务内提交，并使数据版本 +1；
- “立即核对”和“打包下载”都把当时的逐作品结论固化为**只读快照**
  （`snapshots` / `snapshot_works` 表）。核对期间馆员仍可继续补登，
  旧快照结论不受影响；补登后需重新核对/下载；
- 下载前再做一次“恢复份数 → 重新左联接 → 与输入宽表逐组合比对”的自检，
  自检不过或存在冲突/待补作品时拒绝下载——因此**更正后无法唯一拆分，
  新的下载会被停止**。

### 入库增量发布与份号模型

接收库为同一（作品号, 类别[题名/参展], 名称）下的**每一份**同名明细单独
建档，份号在该键内从 1 起编：

- **补入**：从该键历史最大份号 +1 起连续发放（首次发布从 1 开始）；
- **撤销**：减量时从当前最大有效份号起依次向下撤销，撤掉的号**永久停用**；
  即使整项删掉再补回，新补的号仍从历史最大份号接着发，不复用已撤销的号；
- **不逐份展开**：编号状态只存“历史最大份号 + 已撤销区间”
  （`copy_state` / `revoked_ranges`），增量包只存连续号段
  （`package_ranges`），包 CSV 也是一行一个号段。

发布流程（网页“入库增量发布”入口 / JSON 接口）：

1. **计算增量**：用同一已提交状态的宽表和底账做拆分，全部作品都有唯一解
   才按上次发布的份数算增减（首次发布从零起算），生成待提交的发布计划；
   份数无变化时不生成计划、不发包。计算后仍可继续上传宽表或更正底账；
2. **提交发布**：提交时若宽表、底账（数据版本）或最近一包已变动，拒绝并
   提示重新计算（重试）；校验通过则新包与份号状态在**同一事务**内生效，
   任何失败都回滚、保留原发布状态；
3. **凭包号重下**：包 CSV 原文随包保存，重复下载内容一致。CSV 头部注明
   包号与前一包号，正文按作品、类别、名称列出补入或撤销的连续号段。

目标拆分以当前宽表为准：上一包中存在、但当前拆分中已不存在的
（作品, 类别, 名称），其全部有效份号在新包中撤销。

## 2. 目录结构

```
app/
  __init__.py      Flask 路由与页面/JSON 接口
  splitting.py     纯算法：单作品拆分、重新左联接
  publish.py       纯算法：份号区间运算、增量计算、包 CSV 生成
  db.py            SQLite 建表、CSV 解析、事务、快照、份号状态与增量包
  service.py       逐作品评估、核对摘要、打包导出、增量计算/提交编排
  templates/       base/index/work/snapshot/publish_plan/package/error 页面
tests/             pytest：算法分支 11 例 + 端到端 9 例 + 增量发布 12 例
sample_data/       含唯一/待补/冲突三类作品的样例宽表，
                   及增量发布演示用的基准/减量/补入三份宽表
Dockerfile         python:3.11-slim + gunicorn
docker-compose.yml 端口 8000，SQLite 持久化到 ./data
wsgi.py            应用入口
```

## 3. 用 Docker Compose 启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

数据库落在宿主机 `./data/museum.db`。停止：`docker compose down`
（数据保留；`down -v` 不影响绑定挂载，手工删除 ./data 才会清库）。

### 不用 Docker 的本地运行方式

```bash
pip install -r requirements.txt
export SPLIT_DB_PATH=./data/museum.db
python wsgi.py            # 开发服务器，端口 8000
# 或：gunicorn --bind 0.0.0.0:8000 wsgi:app
```

## 4. 操作流程

1. 首页上传 CSV，列名固定为 `作品号,题名,展名,组合次数`（UTF-8/UTF-8 BOM/GBK
   均可；题名或展名留空表示该作品没有此类明细）。重新上传整体替换旧输入。
2. 首页作品列表给出每个作品的状态：**唯一可拆 / 待补底账 / 冲突**，
   待补与冲突的作品号直接列出。
3. 点“登记/更正”进入作品页，可分别登记或更正题名、参展明细的**底账总条数**，
   留空提交即清除该项登记。
4. “立即核对”生成只读快照页；全部唯一后“打包下载”按钮可用，
   下载 zip 内含：
   - `title_details.csv`（作品号, 题名, 份数）
   - `exhibition_details.csv`（作品号, 展名, 份数）
   - `README.txt`（对应快照 ID 与核对说明）
5. “入库增量发布”区：全部唯一后点“计算增量”生成发布计划，计划页核对
   号段无误后“提交发布”打出新包；历史包可随时“重下 CSV”。

另有同能力的 JSON 接口：`GET /api/state`、`POST /api/works/<作品号>/ledger`、
`POST /api/check`、`POST /api/download`（不满足条件返回 409）；
增量发布：`POST /api/publish/calculate`、`GET /api/publish/plans/<id>`、
`POST /api/publish/plans/<id>/submit`（状态已变动返回 409）、
`GET /api/packages`、`GET /api/packages/<id>`、`GET /packages/<id>/csv`。

## 5. 实测结果

测试环境无法安装 Docker（镜像内构建步骤未经本机实跑），因此用本机 Python
+ Flask 测试客户端及真实 HTTP 服务（gunicorn 2 workers，与 compose 一致）
完成验证：

- `pytest tests/`：**32 项全部通过**，覆盖
  - 结构唯一、需底账锁定、错误底账转冲突、清除登记回退待补；
  - 可乘性矛盾、缺失组合、单侧明细、双侧均空、NULL 侧混用、同名归并；
  - 上传替换、坏 CSV 不破坏旧数据、GBK 编码、404；
  - 全流程：上传→核对快照→补登→再核对→打包 zip→更正后下载被拒（409）；
  - 快照冻结：补登后旧快照仍保留当时的 pending/冲突结论；
  - 导出前重新左联接自检，逐组合与输入完全一致；
  - 增量发布：首次从零起编、份数无变化不发包、减量从最大有效份号撤销、
    补入从历史最大份号续发且撤号不复用、整项删掉再补回仍不复用、
    一次撤销跨多个连续号段、计算后上传/更正底账再提交被判失效（409 提示
    重试）、最近一包变动同样判失效、重复提交被拒、提交中途失败整体回滚
    保留原发布状态、凭包号重下 CSV 内容一致。
- 真实 HTTP 试跑（样例见 `sample_data/wide_table_sample.csv`）：
  - G001 结构唯一（题 5 条/展 3 条）、G002 仅题名、G003 仅参展均直接唯一；
  - G004 矩阵存在 4 组可行拆分，页面列出候选总条数，登记题名底账 6 后锁定
    `摹古卷=2、临帖卷=4 / 古籍善本展=3、文献联展=6`；
  - G005 次数矛盾判冲突，下载返回 409；把 G004 底账错改为 7 后同样转冲突、
    下载立即停止，改回 6 恢复；
  - 下载 zip 中两份 CSV 内容与重新左联接自检全部对上。
- 网页“减量后再补入”全流程（gunicorn 实跑，样例见
  `sample_data/publish_demo_{1_base,2_decrement,3_increment}.csv`）：
  1. 上传基准宽表 → 计算 → 提交：包 1 全部补入，各键从 1 起编
     （山水卷 1–2、花鸟卷 1–3、春展 1–1、秋展 1–2、册页甲 1–3、巡展甲 1–2）；
     再算一次提示“份数无变化，不生成新包”；
  2. 上传减量宽表 → 计算 → 提交：包 2 撤销山水卷 #2、册页甲 #2–#3，
     CSV 注明前一包号 1；
  3. 上传补入宽表 → 计算 → 提交：包 3 补入山水卷 #3–#5（历史最大 2 续发，
     撤掉的 #2 未复用）、册页甲 #4–#5（历史最大 3 续发，#2/#3 未复用）；
  4. 计算后又上传新宽表再提交旧计划：页面提示“宽表、底账或最近一包已变动，
     请重新计算后再提交”，计划标记已失效，包数不变；
  5. 凭包号重下包 1 CSV 两次内容逐字节一致；首页显示题名在册 10 份、
     参展在册 5 份；数据库中 `copy_state`/`revoked_ranges`/`package_ranges`
     均为区间存储，未逐份展开。

## 6. 未完成项 / 约束说明

- 交付环境没有 Docker 守护进程，`docker compose up --build` 未在本机实跑；
  Dockerfile/compose 仅做了 YAML 结构与配置项核对（应用代码经 gunicorn
  同级配置实测），需在有 Docker 的环境执行一次首跑确认。
- 并发约定：核对/下载/计算在单个请求内读取最新已提交数据；计算计划时会
  记录数据版本，提交发布用 BEGIN IMMEDIATE 事务串行化，校验不通过即拒绝，
  因此并发提交最多一个成功，其余提示重试。
- 份数以“明细行数”解释；若馆内底账总条数另有口径（如去重名称数），
  需要在登记前按口径换算。
- 目标拆分以当前宽表为准：上一包存在但当前拆分中已不存在的
  （作品, 类别, 名称），其全部有效份号会在新包中撤销（撤号永久停用）。
- 生产部署应通过环境变量 `SECRET_KEY` 注入正式密钥，并在反向代理层加访问控制。
